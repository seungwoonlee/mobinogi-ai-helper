## 1. 리뷰 방법

세 서브에이전트가 같은 설계서를 서로 독립적으로 검토했다.

- 아키텍처 리뷰: 상태 모델, 책임 분리, 복구 전략, 구현 순서
- CLI 안전성 리뷰: 종료 코드, 응답 구조, 동시 호출, 장시간 작업
- 사용자 경험·테스트 리뷰: 첫 실행, 복구 안내, 알림 피로, 접근성, 합격 기준

리뷰어는 파일을 수정하지 않고 발견 사항과 수정안을 보고했다. 아래 내용은 세
보고서의 공통점과 서로 보완되는 사항을 통합한 결과다.

## 2. 종합 결론

연결 감지와 선제 제안을 분리한 큰 방향은 타당하다. 그러나 현재 문서는 게임
연결·AI 연결·작업 상태를 독립적으로 관리한다고 선언하면서 단일 상태표에 다시
섞어 놓았다. 장시간 작업과 주기 조회의 충돌, 결과가 불확실한 명령의 복구,
명령별 응답 구조 차이도 구현 가능한 수준으로 확정되지 않았다.

다음 높은 중요도 항목을 수정하고 재검토하기 전에는 구현을 시작하지 않는다.

## 3. 높은 중요도 발견 사항

### 3.1 상태 축이 서로 섞여 있음

현재 상태표는 게임 상태인 `READY`, 작업 상태인 `BUSY`, 복합 표시인
`DEGRADED`를 하나의 열거형에 포함한다. 이 구조는 `게임 준비됨 + AI 오프라인 +
작업 실행 중` 같은 정상 조합을 표현할 수 없다.

수정 요구:

- `GameConnectionState`, `AIConnectionState`, `CommandState`를 분리한다.
- `DEGRADED`는 내부 원본 상태가 아니라 화면용 파생 상태로만 사용한다.
- 앱 상단에는 게임·AI 대화·현재 작업 배지를 별도로 표시한다.
- 기능 버튼은 세 상태의 조합에 따라 활성화하고 비활성 이유를 보여준다.

### 3.2 상태 전이 규칙이 없음

상태 이름과 시작 순서만 있고, 이벤트가 겹칠 때의 전이 규칙이 없다. 시작 중 게임
종료, 재연결 중 사용자 명령, 절전 복귀, 오래된 비동기 응답 같은 경우 구현자가
임의로 판단하게 된다.

수정 요구:

- `현재 상태 / 이벤트 / 조건 / 다음 상태 / 부수 효과` 전이표를 작성한다.
- 모든 요청에 요청 ID와 세대 번호를 부여한다.
- 오래된 응답이 최신 연결 상태를 덮지 못하게 한다.
- 캐릭터 미접속 상태를 `SESSION_NOT_READY`로 명시한다.

### 3.3 명령 중개기보다 연결 감지를 먼저 구현하도록 되어 있음

설계는 모든 CLI 호출이 `CommandBroker`를 통과해야 한다고 규정하지만 구현 순서는
연결 감지가 먼저다. 이 순서는 초기 폴링과 재시도 코드가 중개기를 우회하게 만든다.

수정 요구:

- `CLI Adapter + 최소 CommandBroker`를 첫 구현 단계로 이동한다.
- 최소 중개기에 직렬화, 요청 ID, 결과 분류, 취소 토큰, 조회 제한 시간을 둔다.
- 채팅·연결 확인·상태 조회·행동 실행이 같은 중개기를 사용하게 한다.
- 현재 `mabinogi_chat.py`의 직접 `subprocess.run` 호출도 이후 공용 어댑터로 옮긴다.

### 3.4 장시간 작업의 생존·취소·종료 정책이 불완전함

장시간 작업 중 모든 감시를 멈추면 CLI 프로세스가 멈추거나 게임이 종료됐을 때
영구 `BUSY`가 될 수 있다. 반대로 호출을 짧은 제한 시간으로 강제 종료하면 게임이
돌려줄 완료·중단 사유와 정리 결과를 잃을 수 있다.

수정 요구:

- 짧은 조회와 장시간 실행의 제한 시간 정책을 분리한다.
- 장시간 실행은 게임 자체 종료 응답까지 기다리고 임의로 강제 종료하지 않는다.
- CLI 자식 프로세스의 생존·EOF·비정상 종료를 별도로 감시한다.
- `RUNNING → CANCELLING → RECOVERING → IDLE/FAILED` 전이를 정의한다.
- 동시 호출 안전성이 검증되기 전에는 앱 내 강제 취소를 제공하지 않는다.
- 앱 종료 시 진행 중 작업을 자동 재실행하지 않고 결과를 `성공`, `실패`,
  `결과 불명`으로 분류한다.

### 3.5 명령별 응답 구조를 분리해야 함

`status` 성공 응답은 `{"pipe":"connected"}`, `capabilities`는
`{"commands":[...]}`, 일반 조회는 명령별 객체·배열, 실행 명령은 주로
`status/body` 구조다. 공통 파서 하나로 모두 처리하면 정상 응답을 오류로 오인할
수 있다.

수정 요구:

- 공통 계층은 종료 코드와 JSON 파싱까지만 담당한다.
- `status`, `capabilities`, 일반 조회, 실행 명령별 검증기를 둔다.
- 예상하지 못한 구조는 `PROTOCOL_ERROR`로 보존한다.
- 실제 응답 표본을 개인정보 제거 후 테스트 자료로 저장한다.

### 3.6 재시도와 결과 불명 상태가 중복 실행을 만들 수 있음

조회 명령과 상태 변경 명령에 같은 자동 재시도 정책을 적용하면 채팅·제작·수거가
중복 실행될 수 있다.

수정 요구:

- 자동 재시도는 기본적으로 조회 명령에만 허용한다.
- 상태 변경 명령은 미실행이 확인된 오류에서만 재시도한다.
- 연결이 끊긴 순간의 실행 결과는 `UNKNOWN_OUTCOME`으로 기록한다.
- 재실행 전에 현재 상태를 조회해 결과를 화해한다.
- 채팅과 행동은 `chat_sent`, `behaviour_sent`로 부분 성공을 따로 기록한다.

### 3.7 첫 실행과 복구 UX가 해결 행동을 제공하지 않음

현재 안내는 상태 설명에 머물러 있어 AI에 익숙하지 않은 사용자가 무엇을 해야
하는지 알기 어렵다.

수정 요구:

- 첫 실행을 `게임 찾기 → 게임 실행 → 설정 확인 → 캐릭터 접속 → 준비 완료`로
  안내한다.
- 상태마다 `다시 확인`, `설정 위치 보기`, `경로 직접 지정`, `진단 정보 복사`
  버튼을 제공한다.
- 연결 실패 중에도 입력 중인 대화와 전송하지 않은 `@@` 문구를 보존한다.
- 복구 시 중단된 기능, 결과 확실성, 다음 행동을 함께 안내한다.

### 3.8 CLI 무응답과 느린 응답 상태가 없음

종료 코드가 돌아오지 않는 경우를 다루지 않아 앱이 `연결 중`에 갇힐 수 있다.

수정 요구:

- 짧은 조회에는 제한 시간을 둔다.
- 제한 시간 초과를 즉시 연결 끊김으로 확정하지 않고 `응답 지연`으로 분류한다.
- 마지막 정상 확인 시각과 수동 `다시 확인` 기능을 표시한다.
- 동일한 주기 조회는 대기열에 누적하지 않고 최신 하나로 합친다.

## 4. 중간 중요도 발견 사항

### 4.1 대기열 우선순위와 폐기 정책

주기 조회를 누적하면 장시간 작업이 끝난 뒤 오래된 요청이 연속 실행될 수 있다.

권장 우선순위:

1. 사용자가 직접 요청한 명령
2. 연결 복구 확인
3. 작업 완료 후 화해 조회
4. 정기 조회

주기 조회는 종류별 최신 요청 하나만 유지하고, `BUSY` 중 놓친 요청은 폐기한 뒤
작업 종료 후 전체 스냅샷 한 번으로 대체한다.

### 4.2 스냅샷 일관성과 유효기간

각 데이터에 `observed_at`, `source_command`, `valid_until`, `quality`를 저장한다.
오래된 값은 화면에 표시할 수 있지만 이벤트 판단에는 사용하지 않는다. 작업 전후
비교는 동일한 작업 ID로 묶는다.

### 4.3 안전 메타데이터 정규화

`requiresConfirm`은 문자열 `"true"` 또는 실제 불리언일 수 있다. 두 형식을
명시적으로 정규화하고 알 수 없는 값은 안전 우선으로 처리한다. `@@` 직접 입력은
사용자의 명시적 전송 요청이라는 별도 정책으로 기록한다.

### 4.4 알림 피로 방지

- 제안을 `긴급`, `도움`, `참고`로 구분한다.
- 진입·복귀 임계값을 다르게 둔다. 예: 가방 90%에서 알리고 80% 아래로 내려간
  후 다시 90%를 넘을 때만 재알림한다.
- `1시간 조용히`, `오늘은 숨기기`, `이 제안 끄기`를 제공한다.
- 최초 스냅샷이라도 즉시 위험한 상태는 예외적으로 한 번 알린다.

### 4.5 AI 연결 상태 세분화

AI 상태는 최소한 `NOT_CONFIGURED`, `CHECKING`, `READY`, `OFFLINE`,
`AUTH_ERROR`, `RATE_LIMITED`를 구분하고, 각각 재시도 가능 여부와 로컬 대체 동작을
정한다.

### 4.6 접근성

- 상태를 색상만으로 구분하지 않는다.
- 키보드만으로 전체 기능을 사용할 수 있게 한다.
- Windows 고대비, 125~200% 배율, 큰 글자, 화면 읽기 프로그램을 시험한다.
- 선제 제안이 입력창 초점을 빼앗지 않게 한다.

## 5. 낮은 중요도와 검증 필요 사항

- 사용자 문구에서 게임의 `MM AI 에이전트`와 대화용 AI를 구분한다.
- 앱 단일 실행 잠금과 게임 명령 잠금을 별도로 설계한다.
- 환경 변수·기본 경로·PATH를 모두 지원하도록 CLI 탐색을 통일한다.
- 이모지 포함 채팅 길이가 게임에서 어떤 단위로 계산되는지 실증한다.
- `status`가 장시간 작업과 동시에 안전한지는 비용 없는 모의 CLI를 먼저 사용해
  검증한 뒤, 실제 게임 검증은 별도 승인 후 수행한다.

## 6. 테스트 계획 보완 요구

기존 테스트 목록을 단순 상황 나열이 아니라 다음 형식으로 바꾼다.

| 사전 상태 | 입력·사건 | 기대 내부 상태 | 사용자 표시 | 사용 가능 기능 | 재시도 규칙 |
|---|---|---|---|---|---|

추가할 필수 사례:

- CLI 접근 권한 거부, 경로에 공백·한글 포함, 버전 불일치
- CLI 무응답, 느린 응답, 비정상 종료, 과도하게 큰 출력
- 연결 상태가 짧은 시간에 반복해서 바뀜
- 앱 종료·절전 복귀 후 스냅샷과 알림 유예 복원
- 외부 프로그램이 동시에 CLI를 사용함
- 작업 도중 앱이 강제 종료됨
- 연결이 끊긴 순간 실행 성공 여부를 알 수 없음
- 사용자가 입력 중일 때 선제 제안이 도착함
- 알림 끄기·유예·오늘 숨기기의 지속성
- 200% 배율, 고대비, 키보드 전용, 화면 읽기

실제 게임 없이 재현 가능한 모의 CLI와 고정 응답 자료를 테스트 산출물에 포함한다.

## 7. 재검토 통과 조건

다음 조건을 모두 만족해야 설계 승인 여부를 다시 검토한다.

1. 세 개의 독립 상태 축과 상태 전이표가 추가됨
2. 최소 `CLI Adapter + CommandBroker`가 구현 순서의 첫 단계로 이동됨
3. 장시간 작업의 대기·취소·앱 종료·결과 불명 정책이 확정됨
4. 명령별 응답 검증과 재시도 정책이 분리됨
5. 첫 실행·오류 해결·복구 UX가 구체화됨
6. 테스트 사례마다 기대 상태와 합격 기준이 작성됨
7. 실제 응답 근거와 모의 CLI 테스트 자료 계획이 연결됨
8. 높은 중요도 미해결 항목이 0개임
